# .space

Everything that makes this fork differ from [abue-ammar/tinycast](https://github.com/abue-ammar/tinycast).
`main` is never edited by hand beyond this folder: it is regenerated as *upstream main + these patches*,
one commit per patch (titled after it, its row below as the message), then one commit with this folder,
the README and `apply.sh`'s rewrites.

## Automation

- **`space-sync.yml`** — every 10 minutes checks upstream `main`. On a new commit (or a manual commit on top
  of the generated one) it first applies the patches on Linux (`check-apply.sh`); a conflict goes to the
  `space-sync` issue and stops there. Otherwise it rebuilds `main` = upstream + patches on macOS, builds,
  runs the tests and force-pushes `main` with the patches re-cut against that upstream. On failure nothing
  is pushed and the issue is opened; a hand-made push to `main` during the build just drops the result.
- **`space-release.yml`** — twice an hour checks upstream's latest stable release. For a tag not yet released
  here it applies the patches to that tag, builds, tests, signs with this fork's `Tinycast Self-Signed`
  identity and publishes the same tag with a DMG and the zip the in-app updater installs.

Upstream's own workflows (`release.yml`, `website*.yml`, `triage.yml`, `coauthors.yml`) are disabled in this
repository's Actions settings.

Secrets: `SIGNING_P12_BASE64`, `SIGNING_P12_PASSWORD` (the signing identity, never rotate it casually —
installed copies only accept updates signed with the same certificate) and `SPACE_PUSH_TOKEN`
(fine-grained token for this repository: Contents + Workflows read/write).

## Changing the patch

Start from the current `main`: its patches are fresh and each one is a commit there. Change the code on
top of that patch's commit, re-cut the file with `git diff --full-index <commit>~1 <commit> -- . ':!Tinycast.xcodeproj'
':!Tinycast/Resources/RaycastRuntime.generated.js' > .space/patches/…`, check that every patch still applies
with plain `git apply` on upstream `main`, commit, and push; the next sync rebuilds `main` with it.

What the sync's failures since September taught (most were a patch meeting an upstream change):

- When upstream ships what a patch does, drop the patch and its rows here — the conflict is the signal.
  The issue lists the upstream commits that touched the conflicting file to make that quick.
- Put new code in new files and keep the hunks in upstream files to a hook of a line or two. Add lines
  rather than rewrite upstream's; a value upstream keeps bumping is a rewrite in `apply.sh`, not a hunk.
  When `private` members keep the code in an upstream file, it goes in an `extension` after the type
  (0001 in `RootPaletteView.swift`). When a model or coordinator can carry a feature, its hooks go there
  rather than into a view (0030 keeps its folder in `PaletteState` and `FileSearchSession`).
  The busiest upstream files are `RootPaletteView.swift`, `AppCore.swift`, `SettingsSearchCatalog.swift`,
  `PaletteWindowController.swift`, `Scripts/run-tests.sh` and the runtime's `fixtures.mjs`.
- Add at most a one-line modifier to upstream's long SwiftUI chains (`stateObservers`, `keyHandlers`),
  its body a call into the fork's code: CI's Xcode 26 gives up type-checking a chain that a newer Xcode
  still builds. Of one view's `onKeyPress` handlers the one later in the chain is asked first, so a fork
  handler that must see a key before upstream's goes after it.
- A test the fork adds never depends on wall-clock timing: CI runners are slow and loaded, and a harness
  whose upstream checks also flake upstream is ignored as a whole by `gate.sh`.
